# AI Engineering Guide — Nasir Bespoke

This is the operating manual for any AI coding agent (Claude, Grok, or otherwise) working in this repository. It states how work here is actually done, verified by the pattern every phase from 3B through 4C has followed identically. Read `NASIR_ARCHITECTURE.md` and `DOMAIN_RULES.md` first — this document tells you *how* to build on top of what they describe.

## Coding expectations

- **Read the sibling file before writing the new one.** Every new domain in this codebase (Order, Fabric, Production) was built by mirroring the immediately preceding domain's file structure and conventions almost line-for-line: a `types.ts` addition, a `repository.ts` interface extension + Prisma implementation, a `permissions.ts` grant, a `validation.ts` state machine (if applicable), a `*-handler.ts` file, thin route files, a fake-repository extension, and a test file. Do not invent a new pattern for a new domain unless the existing pattern genuinely cannot express the requirement — and if so, say so explicitly rather than silently diverging.
- **Snapshot at commitment boundaries; reference everywhere else.** If you are adding a field that captures "what was true when X happened" (an order, a material selection, a stage change), copy the data in. If you are adding a field that should always reflect current reality, use a normal foreign key. Getting this backwards is the single easiest way to break this codebase's core guarantee — see `DOMAIN_RULES.md`.
- **Every mutating endpoint gets an explicit field allow-list.** Use `hasUnexpectedFields(body, ALLOWED_FIELDS)` (from `lib/customer/http.ts`) on every `POST`/`PATCH` handler. Never spread a client body into a database write.
- **Every route handler takes an injectable `dependencies` parameter**, defaulting to the real implementation (`DEFAULT_CUSTOMER_DEPENDENCIES` for the business domain), so it can be tested against `tests/customer-fake-repository.ts` without a real database. New domains extend the same `CustomerRepository` interface and the same fake — do not create a second injection pattern.
- **New status/stage fields get a real state machine**, not a free-form string with ad hoc `if` checks. Define a `Record<Status, Status[]>` transition table plus an `assertValidXTransition()` function in `lib/customer/validation.ts`, mirroring `ORDER_STATUS_TRANSITIONS`/`PRODUCTION_STAGE_TRANSITIONS` exactly.
- **No comments except where the WHY is genuinely non-obvious** — a hidden constraint, a workaround, an invariant a future reader could easily violate by accident. This codebase's existing files are consistently terse; match that, don't pad it.
- **No new abstractions ahead of need.** A bug fix doesn't need a refactor; a one-shot script doesn't need a config system. Three similar lines beat a premature helper.
- **Follow the existing UI conventions exactly** for anything client-facing: `"use client"`, the `isRecord`/`readResponseError` helper pair (copied verbatim into each new component — there is no shared utils file for this, deliberately, to keep each component self-contained), `fetch(..., { credentials: "same-origin" })`, `useEffect` + an `active` boolean flag to avoid setting state after unmount, and reuse of existing CSS classes (`order-detail-section`, `customer-profile-*`, `showroom-cta-button`/`showroom-link-button`, `order-status-pill` and its stage-specific variants) over inventing new ones. Add new CSS into the existing `@media` blocks in `app/globals.css` rather than creating parallel breakpoint blocks.

## Testing expectations

- **`npm test` must never require a real database, Redis instance, or OpenAI key.** Every business-domain test imports `createFakeCustomerRepository()` from `tests/customer-fake-repository.ts` and injects it via the handler's `dependencies` parameter. If you add a repository method, add its fake implementation in the same change — a domain is not done until its fake exists and its tests pass against it.
- **Mirror the existing test file structure**: `beforeEach(() => repository.reset())`, the shared `jsonRequest(url, method, body, headers?)` / `authAs(user)` helpers from `tests/customer-test-http.ts`, section-banner comments (`// ==== CREATE / RETRIEVE ====`), and one test per distinct behavior — not one giant combined test per endpoint.
- **Every new domain needs, at minimum**: create/retrieve happy-path tests, full state-machine coverage (every valid transition, every impossible/terminal-state rejection), a role-permission test per role that touches the domain, and the full security list below.
- **Required security tests for any new mutating endpoint**: reject unauthenticated access (401), reject a cross-origin request (403, using the `{ origin: "https://evil.example", "sec-fetch-site": "cross-site" }` header pattern already used throughout), reject a fake/unknown ID for every resource the endpoint looks up (404), reject a client-supplied `id`/`createdAt`/`updatedAt` (400, unexpected field), reject a client-supplied identity/ownership claim (`createdBy`-style field, 400), reject an unauthorized role attempting the action (403), reject an invalid state transition (400).
- **A test file is not "regression coverage" until the full suite has been run and confirmed green**, not just the new file in isolation — new work has repeatedly (correctly) run `npm test` in full before considering a phase done, because a change to a shared file (`permissions.ts`, `http.ts`, the fake repository) can silently affect every other domain's tests.
- **When something you're testing looks wrong, don't quietly work around it.** During Phase 4C, a QA pass correctly left a failing test in place (asserting the *correct* expected behavior) rather than weakening the assertion, and reported the real bug it had found (a missing `try`/`catch` around a database call, meaning the endpoint would crash instead of failing closed) instead of silently patching or ignoring it. That is the expected standard: a red test that catches a real bug is more valuable than a green test that doesn't.

## Migration rules

- **Every migration is additive.** `CREATE TABLE`, `CREATE TYPE`/`CREATE ENUM`, `CREATE INDEX`, `ADD CONSTRAINT` only. Never `DROP TABLE`, `DROP COLUMN`, or a destructive `ALTER` against a live database. If a schema mistake needs correcting, add a new additive migration to fix it forward — do not edit or delete an already-applied migration file.
- **Generate migrations with `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script -o <file>`**, writing directly to the output file via the `-o` flag. **Never** generate a migration via shell redirect (`> migration.sql`) — this exact mistake happened once (Phase 3B→3C), capturing stray Prisma CLI status-line output into the SQL file and corrupting it; it was found and fixed during Phase 3C activation, and every migration since has deliberately used the `-o` flag specifically to avoid repeating it.
- **Always inspect the generated `migration.sql` before applying it.** Confirm it contains only the statements you expect and nothing destructive, before running `prisma migrate deploy`.
- **Regenerate the Prisma client (`npx prisma generate`) both before writing code against new types and again after applying the migration.** The generated client lives at `lib/generated/prisma` (gitignored) — never hand-edit it.
- **`DATABASE_URL` changes are Preview-only in this deployment.** Production has no database configured, by design (see `KNOWN_LIMITATIONS` in the Phase 3C-4C task reports) — never point `DATABASE_URL` at Production without an explicit, deliberate decision to activate it, and never reuse the Preview/dev database as the Production database when that day comes; provision a separate one.
- **Never run a migration against a database without first confirming you know which database it is.** `.env.local` holding the live connection string is gitignored and must never be echoed into chat, logs, commits, or any report.

## Security rules

- Follow every principle in `DOMAIN_RULES.md`'s "Security principles" section — they are restated here as concrete engineering rules:
  - Same-origin check (`isSameOriginRequest`) and authentication (`authenticate` dependency) run before any repository call, on every state-changing route.
  - Every mutating endpoint has an explicit field allow-list; nothing is ever spread from a client body into storage.
  - IDs, timestamps, ownership, and status/stage fields are always server-set.
  - A resource that doesn't exist and a resource that exists but isn't yours return the identical error — never leak cross-tenant existence.
  - Every handler that touches the repository wraps the call in `try { ... } catch (error) { const mapped = mapDomainErrorToResponse(error); if (mapped) return mapped; throw error; }` so a missing/misconfigured database (`DatabaseConfigurationError`) fails closed with a 503 instead of an unhandled crash. **This exact omission was a real, shipped bug twice** — once in Phase 4B's `handleListFabricsRequest`, once in Phase 4C's `handleListProductionJobsRequest` — both caught by tests specifically written to check the 503-gate on every new list/get endpoint (`tests/customer-database-gate.test.ts`). Any new list/get/create/update handler must be checked against this pattern before being considered done, and a database-gate test added for it.
- **Never call an AI/LLM provider from business-domain code.** The only sanctioned AI call path is `lib/tryon/index.ts` → the provider abstraction, for image generation only, already wrapped in rate limiting and the generation guard. If a future task seems to want an LLM call from Customer/Order/Fabric/Production code, stop and flag it — it almost certainly violates the architecture, and the task instructions across every phase so far have explicitly forbidden it.
- **Never log, print, commit, or otherwise surface a real credential** — database connection strings, API keys, session secrets. `.env.local` is gitignored; verify with `git check-ignore -v .env.local` before touching secret-adjacent work if you're ever unsure.
- **Rotating or reading a Vercel "Sensitive" environment variable is not possible via the tooling available to an agent** (it's write-only once set). If a task needs a Preview test credential you don't have, don't fabricate one or guess — verify the same functionality locally against the same live database instead (dev mode's auth fallback grants full `OWNER` access) and document the Preview-UI gap honestly.
- **Staff allowlist helper is one user per run.** `npm run auth:create-user -- <username> "Display Name" <ROLE>` (`scripts/hash-password.mjs`) requires a TTY, prints `AUTH_USERS_JSON_BASE64=` of a **one-element** JSON array, and does **not** merge. Multi-user Preview allowlists must be merged locally (decode → concat user objects → re-encode) without committing hashes. `AUTH_USERS_JSON_BASE64` wins over `AUTH_USERS_JSON`.
- **Vercel Deployment Protection** on Preview SSO-gates requests before app auth. A 401 `{ protection: { vercel_auth_enabled: true } }` is Vercel, not a Nasir login bug. Do not disable Production protection. Do not treat Preview as QA-complete until an operator can reach `/login`.
- **Do not re-run `20260820120000_add_production_notes`.** The operator applied it to the shared Preview/dev database. Production still must not use that database.

## Things future agents must never do

1. **Never introduce a Staff/User database table** without an explicit, deliberate architectural decision — every `createdBy`/`recordedBy`/`selectedBy`/`changedBy`/`assignedStaffId` field in this schema is a plain username string precisely because no such table exists, and a large surface of code assumes this. `ProductionNote.createdBy` is the same pattern.
2. **Never make `Order.outfitSnapshot`, `Order.measurementSnapshot`, or `OrderMaterialSnapshot`'s descriptive fields into live joins/references.** Live Fabric/FabricVariant edits (Phase 4E) must never rewrite historical material snapshots. This would silently break "an order must remain readable exactly as it was placed" for every existing order in the database, retroactively, with no migration path back.
3. **Never accept a client-supplied snapshot, ID, timestamp, or identity field on any endpoint**, even "just for testing" or "just this once." Add it to a legitimate allow-list only if the server is genuinely meant to trust that specific field from that specific caller (rare — check the existing allow-lists for precedent first).
4. **Never run a destructive migration** (`DROP`/destructive `ALTER`) against the live database, and never delete or edit an already-applied migration file.
5. **Never merge into `main` or deploy to Production** without the user explicitly asking for it in that exact turn. Every phase from 3B onward has worked exclusively on `feature/split-outfit`, verified via Preview deployments only, and this has been treated as a hard rule, not a default that can be inferred as "probably fine now."
6. **Never call OpenAI (or any other AI provider) from anywhere outside the existing `lib/tryon/` provider abstraction.** Every phase's task instructions have explicitly forbidden this for business-domain work, and it has never happened.
7. **Never weaken a test assertion to make a red test pass without first understanding whether the test caught a real bug.** Two real bugs in this codebase's history were caught exactly this way; both were fixed in the implementation, not the test.
8. **Never build ERP functionality** (pricing, invoicing, inventory/stock counts, supplier ordering, scheduling/capacity planning, costing) into the Order/Fabric/Production domains without an explicit task asking for it by name — every phase touching these domains has been given, and has respected, an explicit "this is NOT an ERP" boundary.
9. **Never skip the field-allow-list step** on a new mutating endpoint "because the client will only ever send the right fields anyway." The allow-list is the actual security control, not a formality.
10. **Never leave a new list/get/create/update handler without the `try`/`catch` → `mapDomainErrorToResponse` guard.** Check for it explicitly; it has been missed twice already.
