# Nasir Bespoke — Domain Rules

This document states the non-negotiable business rules for each domain, as actually implemented. Where a rule is enforced in code, the enforcing file is named — treat that file as the rule's source of truth if this document and the code ever disagree (and flag the discrepancy rather than silently trusting either one).

## Customer rules

- A customer is identified by a **unique phone number** (`Customer.phone`, unique constraint; `DuplicatePhoneError` on collision). Name is required; email is optional.
- Preferences (`preferredStyles`, `preferredColours`, `preferredFit`, `preferredOccasions`) are **closed-vocabulary fields only** — validated server-side in `lib/customer/validation.ts` against fixed value lists (`CUSTOMER_PREFERRED_COLOUR_VALUES`, `CUSTOMER_PREFERRED_FIT_VALUES`, plus the reused Phase 3A `StylePersonality`/`ShowroomOccasion` taxonomies). **Never free text.** This is deliberate: it keeps preferences queryable and prevents the field from becoming an inferred-personality/appearance dumping ground.
- Nothing about a customer's appearance, ethnicity, or personality is ever inferred or stored. The only preference data that exists is what the customer explicitly told staff.
- Customer records are never AI-generated. There is no code path where an LLM writes to a Customer row.
- Deleting a `Customer` cascades to `MeasurementProfile`, `ShowroomSession`, `SavedOutfit`, and `Order` (all `onDelete: Cascade` from Customer). This is a real, destructive operation — there is currently no soft-delete or archival mechanism. Treat customer deletion as something a future phase should gate much more carefully before ever exposing it broadly (see `NASIR_ROADMAP.md`).

## Measurement rules

- Measurements are **append-only**. `MeasurementProfile.version` is a strictly increasing, per-customer integer; a new measurement is always the *next* version, never an edit of an existing one (`createMeasurementVersion` in `lib/customer/prisma-repository.ts` computes `(latest?.version ?? 0) + 1`). There is no update or delete path for a measurement version anywhere in the codebase.
- Each of the three garment blocks (`jacketMeasurements`, `trouserMeasurements`, `shirtMeasurements`) is a `Json` column, but is **not** an uncontrolled blob: every write is validated against a versioned allow-list of field names (`lib/customer/measurement-fields.ts`), and every value must be a finite number strictly between 0 and 200 (`validateMeasurementBlock` in `lib/customer/validation.ts`). An unknown field name or an out-of-range/non-numeric value is a 400, not a silent drop.
- `recordedBy` is always the authenticated staff username, server-derived — never client-suppliable.
- **An order can never be created for a customer with no measurement on file.** `MeasurementRequiredError` is thrown in `lib/order-handler.ts` if `getMeasurementHistory` returns empty.
- **A later measurement version never changes an already-placed order.** `Order.measurementSnapshot` is a full copy of the *latest* `MeasurementProfile` at the moment the order was created, not a reference — this is verified by a dedicated regression test (`tests/order.test.ts`: "a later measurement version never changes an already-placed order's snapshot").

## Order snapshot rules

This is the single most load-bearing rule set in the whole system. An **Order** exists specifically to preserve historical truth at the moment a customer commits to a purchase — it must remain fully, exactly readable in the future even if every other record it was built from later changes.

- `Order.outfitSnapshot` is a **full copy** of `SavedOutfit.outfitSnapshot` at order-creation time (the complete validated `FinalOutfitSnapshot` — component IDs, material groups, recipe status, provenance — not just a foreign key to the SavedOutfit). Reconstructed server-side in `lib/order-handler.ts`'s `handleCreateOrderRequest`, never accepted from the client.
- `Order.measurementSnapshot` is a **full copy** of the customer's latest `MeasurementProfile` at that same moment (version number, all three garment blocks, who recorded it, when) — same rule as above.
- **The client can never submit either snapshot.** `POST /api/customers/{id}/orders` accepts exactly one field, `savedOutfitId` — the field allow-list in `lib/order-handler.ts` rejects anything else (including a client-supplied `outfitSnapshot`, `measurementSnapshot`, `status`, `id`, `createdAt`, or `createdBy`) with a 400.
- A `savedOutfitId` that doesn't exist, or that exists but belongs to a *different* customer, both resolve to the identical `SavedOutfitNotFoundError` → 404 — the API deliberately never distinguishes "doesn't exist" from "not yours," so a probing client can't learn whether an ID exists for someone else.
- `Order.status` follows a strict state machine (`ORDER_STATUS_TRANSITIONS` in `lib/customer/validation.ts`): `DRAFT → CONFIRMED → TAILORING → TRIAL ⇄ ALTERATION → QUALITY_CHECK ⇄ ALTERATION → READY → DELIVERED`, with `CANCELLED` reachable from any non-terminal state and `DELIVERED`/`CANCELLED` both terminal. No status update ever skips a step or reverses past a completed one. Order creation is a STAFF-permitted action (the natural conclusion of the showroom flow); every status change after that is MANAGER/OWNER-only — see `PERMISSIONS.md`.
- This is explicitly **not** an ERP: no pricing, payment, or invoicing fields exist on `Order` (see `NASIR_ROADMAP.md` for whether/when that changes).

## Fabric rules

- Fabric catalogue entries (`Fabric`, `FabricVariant`) are **curated business data, entered by staff — never AI-generated, never inferred**. There is no code path where any AI provider writes to these tables.
- This is explicitly **not inventory or supplier management**: no stock counts, no per-location quantities, no reorder thresholds, no pricing anywhere in the schema. `FabricVariant.isAvailable` is a simple staff-set boolean flag, not a quantity.
- `Fabric.status` (`ACTIVE`/`INACTIVE`) gates whether a fabric can be **newly selected** — a retired (`INACTIVE`) fabric is rejected with `InvalidMaterialSelectionError` → 400 when a client tries to attach it to an order, even though it (and any order that already used it) remains fully readable forever.
- `OrderMaterialSnapshot` follows the exact same copy-not-reference rule as `Order.outfitSnapshot`: `fabricName`, `composition`, `weight`, `season`, `colour`, `supplier`, and `variantColour` are all copied at selection time in `lib/order-material-handler.ts`, never re-derived from the live `Fabric`/`FabricVariant` rows on read. The `fabricId`/`fabricVariantId` foreign keys are kept alongside the copy purely for traceability and to structurally prevent deleting a fabric/variant that's in use (`ON DELETE RESTRICT`) — the app never joins through them to display an order's materials.
- The client can only ever submit `{ role, fabricId, fabricVariantId? }` when attaching a fabric to an order — never the descriptive fields directly, which would let it forge a snapshot that doesn't match any real fabric. The server independently re-fetches and re-validates the fabric (and variant, if given: must belong to the named fabric and be `isAvailable`) before building the snapshot.
- One `OrderMaterialSnapshot` row per `(orderId, role)` (`@@unique` constraint) — re-selecting a role's fabric **replaces** the prior row (`upsert` in `lib/customer/prisma-repository.ts`'s `setOrderMaterial`). This is a live, correctable selection, not an append-only history like measurements — the current choice is what matters, and it is still permanently attached to the order once the order itself is later read back (there is no mechanism to change a material selection after the fact through the UI beyond re-saving the same role).
- Material roles are a **closed set**: `SUIT_FABRIC | SHIRT_FABRIC` only (`MATERIAL_ROLE_VALUES` in `lib/customer/types.ts`). Extending this set is a deliberate schema-adjacent decision (the `MaterialRole` Postgres enum), not something to do casually.

## Production rules

- One `ProductionJob` per `Order` — enforced at the database level (`ProductionJob.orderId` is `@unique`). Creating a second job for the same order is rejected with `ProductionJobAlreadyExistsError` → 409.
- `ProductionJob.currentStage` follows a strict 10-stage state machine (`PRODUCTION_STAGE_TRANSITIONS` in `lib/customer/validation.ts`): `CONFIRMED → FABRIC_READY → CUTTING → STITCHING → FIRST_TRIAL ⇄ ALTERATION`, `FIRST_TRIAL → FINAL_QC ⇄ ALTERATION`, `FINAL_QC → READY_FOR_DELIVERY → COMPLETED`, with `CANCELLED` reachable from any non-terminal stage. `COMPLETED`/`CANCELLED` are both terminal.
- **The current stage is never the only record of what happened.** Every stage change — including job creation itself (`fromStage: null → CONFIRMED`) — writes a new `ProductionStageHistory` row, in the same database transaction as the `currentStage` update (`lib/customer/prisma-repository.ts`'s `createProductionJob`/`updateProductionJobStage`, both wrapped in `client.$transaction`). There is no update-in-place path for history rows; they are append-only.
- `assignedStaffId` is a **plain staff username string**, never a database foreign key (none exists — see `NASIR_ARCHITECTURE.md`). Shape is the same username pattern the auth allowlist uses (`/^[a-z0-9._-]{2,64}$/` in `validateAssignedStaffId`). Non-null values are then checked against a safe projection of that allowlist: only a `MASTER_TAILOR` identity may be assigned (`lib/customer/staff-directory.ts`). There is still no Staff table.
- Reassigning a job (changing `assignedStaffId` on a stage-update request) is restricted to OWNER/MANAGER, independently of whether the stage transition itself is otherwise valid for the caller's role.
- Moving a job to `CANCELLED` is restricted to OWNER/MANAGER, regardless of the job's current stage or who it's assigned to.
- Role-scoped update rules (enforced in `lib/customer/permissions.ts`'s `canUpdateProductionJob`, on top of the flat `production:update` grant): a `MASTER_TAILOR` may only update a job whose `assignedStaffId` matches their own username, and may not make the FINAL_QC outcome decision (`FINAL_QC → READY_FOR_DELIVERY`/`FINAL_QC → ALTERATION`); a `QC_STAFF` may only act when the job is *currently at* `FINAL_QC`. Full detail in `PERMISSIONS.md`.
- Role-scoped read rules: a `MASTER_TAILOR` reading/listing jobs only ever sees jobs assigned to them — a job assigned to someone else returns 404 (not 403; the API never distinguishes "doesn't exist" from "not yours," same convention as `SavedOutfitNotFoundError`).
- This is explicitly **not** an ERP, inventory, or scheduling system: no costing, no material-consumption tracking, no capacity planning anywhere in the schema or handlers.

## Security principles

These apply uniformly across every domain in this codebase (generation and business alike) and are enforced in shared code, not re-implemented per domain.

- **Same-origin enforcement on every state-changing request.** `lib/request-security.ts`'s `isSameOriginRequest()` checks `Sec-Fetch-Site` and validates the `Origin` header against the request's own host (plus any explicitly configured `AUTH_ALLOWED_ORIGINS`) — applied via `authorizeStaffRequest()` in `lib/customer/http.ts` for every business-domain route, and independently for the generation routes.
- **Authentication before anything else.** Every route handler calls its authenticate dependency (`requireRequestUser` in production) before touching a repository or parsing a meaningful body; an expired/missing session is a 401.
- **Authorization is a flat action-grant table plus, where the domain requires it, resource-level scoping layered explicitly on top** (never resource-level-only, never bypassing the flat grant). See `PERMISSIONS.md` for the complete table.
- **Explicit field allow-lists on every mutating endpoint.** `hasUnexpectedFields()` (`lib/customer/http.ts`) rejects any request body field not on that endpoint's declared allow-list with a 400 — this is what makes client-supplied IDs, timestamps, identities, and snapshot forgeries structurally impossible rather than merely discouraged.
- **The server is the sole author of IDs, timestamps, ownership, snapshots, and status/stage values**, everywhere, without exception. A client never sets `id`, `createdAt`, `updatedAt`, `createdBy`/`recordedBy`/`selectedBy`/`changedBy`, or any snapshot field directly.
- **"Not found" and "not yours" are deliberately indistinguishable** wherever a resource could belong to a different customer/order/staff member than the requester — this prevents ID-probing from leaking cross-tenant existence information.
- **Fail closed, never fail open.** Every domain that depends on external infrastructure (Postgres, Upstash Redis, the real OpenAI provider) returns a clean, typed error (usually 503) when that infrastructure isn't configured or reachable, rather than crashing, silently succeeding, or falling back to an insecure default. See `AI_ENGINEERING_GUIDE.md` for the exact pattern every handler must follow, including a real bug (found and fixed during Phase 4C) where a handler was missing this guard.
- **No AI/LLM call ever writes directly to a business-domain table**, and no business-domain route ever calls an AI provider. The only AI integration point in the entire app is the try-on image generation path (Level 1 catalogue and Split Outfit), which is itself rate-limited, lock-guarded, and idempotency-protected against abuse and double-billing.
